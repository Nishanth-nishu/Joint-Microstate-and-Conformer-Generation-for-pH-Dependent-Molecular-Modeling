## Proposed resolution of D-101 (please confirm or amend)
- The pool for each molecule has n_i = max(N0, c_max·2K_i) conformers, drawn in one ETKDG + TD call. The **first N0
  conformers form a K-free block**: it has the same size for every molecule and is distributed exactly as an N0-only
  run, whatever n_i is.
- Track P arms read the prefix [0, c·2K_i); K only fixes the benchmark's output size. The ORACLE headroom recompute
  reads only [0, N0).
- A test asserts that no arm's demand ever exceeds n_i ("the cap never binds") and that no arm reads n_i.

## Questions

2. Should the N0 block be drawn on sampling seed 0 only (seeds 1–2 then draw 4K_i), or on all three seeds
   (+≈ 2.3 GPU-h)?
3. Allocation is dropped for Stage A (DECISION.md). Is the uncapped ORACLE headroom recompute still wanted, to restate
   the 0.0042 Å figure correctly? (The static rule would be cross-fitted on test and labelled ORACLE.) Or should the N0
   block be dropped altogether, saving ≈ 1.1 GPU-h?

## Answer (SAMPLE)
Date 2026-10-16. Spec revised: EXP-5 §12.1 ("Revised after D-101 …").

**Decision: your design is adopted, with one correction to the pool size.**
- **Sampling seed 0.** N_i = max(128, 4K_i) conformers, drawn in one call. Columns [0, 128) are the K-free block,
  [0, 2K_i) are P0, and [0, 4K_i) are the P1/P3 proposals.
- **Sampling seeds 1 and 2.** N_i = 4K_i each.
- **The cap never binds.** The test asserting this ("no arm reads N_i; every arm reads a prefix") is required.

1. **N0 = 128: yes.** Uniform allocation at 2x needs ≈ 55 conformers per molecule, so no K-free rule up to 2x is
   capped. Only the oracle can reach 128, and its cap-binding share is printed. 128 alone does **not** cover Track P:
   the QM9 test csv has K up to 727, and 80 molecules have 4K > 128 [E-SAMPLE-054]. That is why the pool is
   max(128, 4K).
2. **Seed 0 only.** The block is an analysis object, and 128 i.i.d. draws per molecule are enough for exact
   hypergeometric curves (`curves.py`). Seed 0's pool costs ≈ 1.4 GPU-h and seeds 1–2 ≈ 0.5 GPU-h each
   [E-SAMPLE-054, -053].
3. **Keep the recompute.** It is CPU-only and labelled ORACLE, with the static rule cross-fitted on test and labelled
   ORACLE-informed. It closes D-101 with an uncapped number. No decision is attached unless the user reopens Track D
   (EXP-5 §11 K1, revised). The reason to keep it: V5 showed that the 0.0042 Å figure the drop was based on is a
   capped *lower* bound (D-101; E-SAMPLE-023 revision note), so the record must carry the uncapped value.
